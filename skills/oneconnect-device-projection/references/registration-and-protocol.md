# Registration and protocol packaging

## Child identity versus product identity

The bridge generates child runtime identity material:

- `sn` and `udid` are generated and persisted per child key;
- `mac` is derived from the child serial in the current Python bridge;
- cloud `devId`, PSK, secret, and auth material come from `batchBind` and must not be put in YAML.

The user YAML supplies the product/model description and service selection. The parent gateway's own identity remains fixed by the integration.

## Product fields

At minimum, a user-defined product needs:

```yaml
product:
  prod_id: <mainHelp.DeviceId>
  sub_prod_id: "<Profile/catalog sub-product variant or empty when absent>"
  device_type: <Profile.deviceTypeId or mainHelp.DeviceTypeId>
  manufacturer: <Profile.manufacturerId or mainHelp.ManufacturerId>
  model: <Profile.deviceModel or mainHelp.DeviceModel>
  device_name: <display name>
  protocol_type: <wire protType integer>
  setup_type: 0
  known_fields_only: true|false
  services: [...]
```

Do not invent a sub-product value. If the Profile/catalog does not define one, use an empty string only with `known_fields_only: true` so the bridge omits `subProdId`/`setupType` for sparse models.

The current bridge keeps `hiv/fwv/hwv/swv` on the integration side. They come from `manifest.json`/runtime and are not user YAML fields. This is distinct from the early WSL ZJ0V minimum probe, which intentionally omitted all version fields.

## Observed evidence

The WSL ZJ0V probe succeeded with a sparse `devInfo` containing `sn`, `udid`, `model`, `devType`, `manu`, `prodId`, `mac`, `deviceName`, and `protType: 1`; it omitted `subProdId`, `setupType`, and version fields in that experimental harness. The current bridge's version policy is intentionally different: versions are generated by the integration.

The WSL product-prototype observations also showed that `subProdId` and `protType` are meaningful wire fields, not arbitrary display metadata. A change from `subProdId: "00"` to `"01"` and from `protType: 6` to `5` was tested as a same-length wire patch for a PLC product variant. Treat such values as product-specific evidence.

## Registration diagnosis

When `batchBind` fails:

1. preserve the exact `devInfo` sent;
2. capture the response's `errcode`, `successList`, and `failureList`;
3. compare product identity and protocol fields to the Profile and a known successful trace;
4. test a sparse `known_fields_only` shape only when the Profile does not document the omitted fields;
5. do not conclude that a catalog candidate is accepted until `batchBind` succeeds.

`devInfoSync` and `statusSync` are separate phases. A successful `batchBind` does not guarantee that the later Profile/service model is accepted; validate both registration and subsequent state/command paths.
